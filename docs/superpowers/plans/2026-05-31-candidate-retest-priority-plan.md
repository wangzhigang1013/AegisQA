# Candidate Retest Priority Plan

## 背景

候选资产中心已经支持审批、生成 Workflow 草稿、复跑、晋升审批、baseline 应用/回滚和变更提醒，但当候选数量变多时，用户仍需要人工判断每个候选下一步应该做什么。特别是候选可能处在“还没草稿”“草稿未发布”“草稿已发布可复跑”“已复跑待看报告”等不同状态，单纯按更新时间排序会让高优先级、逾期或已升级候选被淹没。

## 目标

- 后端提供候选资产复跑优先级计划接口。
- 每个候选输出下一步动作、优先级分数、排序原因和可打开入口。
- 前端候选资产中心展示复跑优先级卡片，帮助用户直接判断“先处理谁、怎么处理”。
- 保持候选状态筛选一致：页面当前筛选条件同步作用于候选列表与复跑计划。

## 实施步骤

1. 用后端测试锁定缺口：
   - 准备已发布草稿、未发布草稿、无草稿、已复跑四类候选。
   - 断言接口返回 summary、排序、next_action 和 reasons。
2. 实现后端接口：
   - `GET /prompt-skill-candidates/retest-plan`
   - 输出 `ready_for_retest`、`needs_publish`、`needs_draft`、`already_retested`、`overdue`、`escalated`。
   - 按可复跑、逾期、已升级、审批状态、晋升建议加权排序。
3. 用前端测试锁定缺口：
   - 候选资产中心必须展示“复跑优先级”。
   - 展示可直接复跑候选、待发布候选和排序原因。
4. 实现前端：
   - 新增 `PromptSkillCandidateRetestPlan` 类型。
   - API client 接入 `promptSkillCandidateRetestPlan`。
   - 候选资产中心新增复跑优先级卡片、summary 标签、下一步动作和入口按钮。
5. 同步状态文档与验收矩阵。
6. 跑定向验证和全量验证后提交。

## 验收标准

- 后端目标测试从失败变为通过。
- 前端目标测试从失败变为通过。
- 候选资产中心能展示候选复跑优先级、原因和下一步入口。
- 所有候选治理动作成功后刷新工作量和复跑计划缓存。
- 全量后端、前端、构建、E2E 和 diff 检查通过。
